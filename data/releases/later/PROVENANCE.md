# Provenance log: original Bitcoin release binaries, 0.2.0 to 0.3.19 (2009-12 to 2010-12)

Compiled 2026-09-26. All retrieval times are UTC. The machine-readable versions are `MANIFEST.json`, `SHA256SUMS`, `SHA1SUMS`, `MD5SUMS` and `swh_download_log.jsonl`, all in this directory.

## Summary

- I obtained **61 original release files**: every Windows ZIP, NSIS installer, Linux tarball and Mac ZIP that SourceForge listed for Bitcoin 0.2.0 through 0.3.19, except four (listed below).
- **All 61 match, byte for byte, the SHA1 *and* MD5 that SourceForge itself published for each file at the time.** SourceForge embedded those hashes in the JSON on its file-browser pages. The Wayback Machine captured those pages from 2010-12 to 2011-05, before Gavin Andresen deleted the pre-0.3.24 binaries in 2012. SourceForge computed the hashes over the bytes it was serving.
- **The four 0.3.10 files also match the SHA1 hashes Satoshi Nakamoto posted himself** on bitcointalk on 2010-08-15 (topics 823 and 827). I also checked this against the live bitcointalk pages today.
- **Immediate source of the bytes:** the Software Heritage archive (archive.softwareheritage.org), which is content-addressed. For each file I requested the content by the SHA1 SourceForge published, and it came back. Software Heritage's public API won't say which crawled origin (repository) the blobs came from; the provenance endpoint needs an authenticated token. See "Upstream origin" below.
- **Not found:** `bitcoin-0.3.8-win32.zip`, `bitcoin-0.3.15-linux.tar.gz`, `bitcoin-0.3.15-win32-setup.exe`, `bitcoin-0.3.19-linux.tar.gz` and `bitcoin-0.1.5.rar`. I also didn't find any of Satoshi's bitcoin.org/download test builds (0.3.1rc2, 0.3.2.5, 0.3.9rc1/rc2, 0.3.13rc1, 0.3.13.1-specialbuild, 0.3.13.2, linux64-0.2.7.1). For each one I know the SourceForge SHA1/MD5 or Satoshi's SHA1 where they exist, so any copy found later can be verified.
- I haven't analysed contents beyond `file(1)` and hashing. The files are not repacked. They are the exact blobs whose SHA1+MD5 SourceForge published, so all the internal metadata (ZIP/tar/gzip headers, NSIS, PE) is original.

## How authenticity was established

1. **SourceForge-published hashes (contemporaneous, third-party computed).** SourceForge's 2010-2011 file browser (`sourceforge.net/projects/bitcoin/files/Bitcoin/bitcoin-X/`) embedded a JSON blob per file of the form
   `"bitcoin-0.3.0-win32.zip": {"sha1": "f6453e7978b309da201a3061a7257837d8fe0ce6", ..., "md5": "82895ecc531e77027d7da96fc07fee0a", ...}`.
   I downloaded every archived capture of these pages from before the deletion (raw, via `id_`). They are in `sf-files-pages/`, with their original URLs and timestamps in `sf-files-pages/_capture_urls.txt`. The extracted hashes are in `sf_published_hashes.json`, 75 files covering 0.2.0 to 0.3.20.2. Every file was checked against both SHA1 and MD5. Where a file appears in several captures, the hash is the same in all of them.
   - Earliest hash-bearing captures: 0.2.0 on 2010-12-10; 0.3.17 on 2010-12-10; 0.3.19 on 2010-12-20, eight days after release; all other 0.3.x in 2011-05. The same pages list each file's SourceForge date as its original 2010 date, i.e. no re-upload is visible (but see caveat 3).
2. **Satoshi-published SHA1s (verbatim).** These are in `published-hashes/satoshi_bitcointalk_sha1.txt` (hash lines) and `published-hashes/satoshi_bitcointalk_posts_with_hashes.txt` (full posts). Live copies of the bitcointalk pages fetched 2026-09-26 are `published-hashes/bitcointalk_topic*_live_20260926.html`. The key post is https://bitcointalk.org/index.php?topic=827.msg9590#msg9590 ("Version 0.3.10 - block 74638 overflow PATCH!", 2010-08-15 23:48:22 UTC; last edited by satoshi 2010-08-16 13:10:56), verbatim:
   ```
   Download from sourceforge:
   http://sourceforge.net/projects/bitcoin/files/Bitcoin/bitcoin-0.3.10/

   SHA1 16645ec5fcdb35bc54bc7195309a1a81105242bb bitcoin-0.3.10-win32-setup.exe
   SHA1 4f35ad7711a38fe8c880c6c9beab430824c426d3 bitcoin-0.3.10-win32.zip
   SHA1 e3fda1ddb31b0d5c35156cacd80dee6ea6ae6423 bitcoin-0.3.10-linux.tar.gz
   SHA1 b812ccff4881778b9090f7c0b0255bcba7b078ac bitcoin-0.3.10-macosx.zip
   ```
   The same Windows/Linux hashes also appear in https://bitcointalk.org/index.php?topic=823.msg9573#msg9573 and https://bitcointalk.org/index.php?topic=823.msg9584#msg9584 (bitcoin.org/download links). These are the only official-release hashes Satoshi posted. He also posted hashes for test builds, none of which I found:

   SHA1 9fc44ea5f2109618073e2cfd887e2cc266eb31a9 bitcoin-0.3.13.1-specialbuild-linux64.tar.gz (topic=1327.msg15110)

3. **Mirror directory listings (supporting metadata).** Archived Apache index pages of the iWeb SourceForge mirror (`iweb.dl.sourceforge.net/project/bitcoin/Bitcoin/...`, crawled 2011-05 to 2012-07) are in `sf-mirror-listings/`, parsed in `sf-mirror-listings/listing_summary.tsv`. They give each file's mirror mtime (mirror-local time. iWeb is in Montreal, UTC-5 in winter and UTC-4 in summer, and the listings are exactly that far behind the SourceForge UTC dates) and size, for 0.2.0 to 0.3.24. Examples: bitcoin-0.2.0-win32.zip 16-Dec-2009 16:03; bitcoin-0.3.0-win32.zip 06-Jul-2010 11:12; bitcoin-0.3.19-win32.zip 12-Dec-2010 17:38.

## Obtained files

"Retrieved from" is the Software Heritage content URL. The earlier downloads used `/api/1/content/sha1:<sha1>/raw/`. The rest used the equivalent `/browse/content/sha1:<sha1>/raw/`, because the REST API allows 120 requests per hour and the browse endpoint serves the same blob. Every download was re-hashed locally, and the full per-file timestamps are in `swh_download_log.jsonl`. Each file's Software Heritage persistent ID (`swh:1:cnt:<git-blob-sha1>`) is in `MANIFEST.json`. The "SF-listed file date" comes from the SourceForge page and is **not necessarily the upload time of these exact bytes** (caveat 3). The Mac OS X builds were made by Laszlo Hanyecz, not Satoshi ("Mac OS X version (thanks to Laszlo)", 0.3 announcement, topic=238.msg2004; "Thanks Laszlo for the Mac OSX build!", 0.3.13). I kept them for completeness.

## Upstream origin of the Software Heritage blobs (unresolved)

Software Heritage stores content by hash. Mapping a blob back to the repository or tarball it was crawled from needs the authenticated `provenance/whereis` API, which I don't have. One strong lead: SWH has the origin `https://github.com/achow101/bitcoin-binaries` (GitHub user achow101 = Andrew Chow, Bitcoin Core developer). It was visited 2016-09-08, 2017-09-24, 2017-11-09, 2019-01-11, 2019-06-04, 2019-11-18 and 2020-02-28 with status `partial` and no snapshot, which is typical for a repository of large binary blobs. By 2021-05-19 it was `not_found`, and the GitHub repo now returns 404. I have **not** verified that the blobs came from there. None of this affects authenticity, which rests on the SHA1+MD5 match with SourceForge's own published hashes (and, for 0.3.10, Satoshi's).

## Caveats

1. What's proven is byte identity with the file SourceForge served when each page was captured: 2010-12 for 0.2.0, 0.3.17 and 0.3.19, and 2011-05 for the other 0.3.x. That is also what the SourceForge mirrors held in 2011 (the iWeb listings agree on sizes and 2010 mtimes). For 0.3.10 identity with Satoshi's own build is proven directly by his SHA1s. For the other files it rests on the absence of any replacement between release and capture. Nothing points to a replacement, but SourceForge access passed to Gavin Andresen and others during early 2011.
2. SHA1 alone is not collision-proof for adversarial files. Each file here matches **both** SHA1 and MD5 as published by SF, plus the exact length (SWH), which is far beyond any practical collision attack on these particular 2010 files.
3. The SourceForge "date" column is not a reliable upload timestamp for these bytes. For example, bitcoin-0.3.0-linux.tar.gz is SF-dated 2010-06-24 23:02:00 UTC (iWeb 19:02 local), but its gzip header mtime reads 2010-06-25 22:48:07 (from `file`). Many win32.zip entries show a suspicious `xx:01:00` time. Use these dates only as a lead.
